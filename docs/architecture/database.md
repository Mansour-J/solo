# Database

PostgreSQL 18, schema `solo`, managed only by versioned Flyway SQL migrations in
`database/migrations`. Clients never connect to it; the API connects as `solo_app`.

## Conventions

- **Files:** `V<n>__<what_changed>.sql`, `n` increasing by one. Naming is validated by Flyway.
- **Never edit an applied migration.** Add a new one. Prefer additive, backwards-compatible changes
  (add nullable column → backfill → constrain in a later release) so an old API version keeps working
  during a rolling deploy and rollback stays possible.
- **Keys:** `uuid` primary keys (UUIDv7, generated by the API; `uuidv7()` default as a fallback).
- **Money:** `bigint` minor units + `char(3)` currency. Rates and percentages: `numeric`. No floats.
- **Enumerations:** `text` + `CHECK (… IN (…))`; easier to extend than Postgres enums.
- **Tenancy:** every table with `business_id` must:
  1. reference `businesses (id) ON DELETE CASCADE`;
  2. call `SELECT enable_tenant_isolation('<table>');` (row-level security + `updated_at` trigger);
  3. grant only the privileges the API needs to `solo_app`.
  `database/tests/schema_checks.sql` fails CI if any of this is missing.
- **No credentials:** there are no accounts, so no passwords or tokens are stored (V14 dropped them; ADR 0016). `users` holds the owner's name and preferences.
- **Audit:** `audit_logs` is append-only for the API (no `UPDATE`/`DELETE` grants).
- **Reference data** (tax rates) is versioned by effective date (`effective_from`, exclusive
  `effective_to`) with an exclusion constraint preventing overlaps.

## Roles

| Role | Used by | Notes |
|---|---|---|
| owner (`POSTGRES_USER`; `postgres` in the desktop app) | Migrations | Owns every object. Never used by the API |
| `solo_app` | The API | `LOGIN`; subject to row-level security. The desktop app gives it a new random password on each start |

The development database's init script (`infra/docker/postgres/init`) creates `solo_app` as a login
role with `APP_DB_PASSWORD`; the desktop app's local server creates it itself (`services/local`). V1
creates it `NOLOGIN` if it doesn't exist.

## Request context

```sql
SELECT set_config('solo.user_id', $user, true), set_config('solo.business_id', $business, true);
```

Both are transaction-local. Policies use `current_app_user_id()` and `current_business_id()`;
`is_business_member()` is a `SECURITY DEFINER` helper so the `businesses` policy can list a user's
businesses without recursing through `business_members`.

## Integrity rules worth knowing

- **Composite foreign keys** `(business_id, x_id) → x (business_id, id)` make it impossible for a
  record to reference another business's customer, account or invoice, even before row-level security.
- **The journal is append-only for the API** (only `SELECT, INSERT` granted) and a deferred
  constraint trigger rejects any entry whose debits and credits differ. Corrections are reversing
  entries (see [financial-model.md](financial-model.md)).
- Business deletion still removes journal rows: cascading deletes run as the table owner.
- Totals are stored with documents (`CHECK (total = subtotal + gst_total)`, and per line
  `total_amount = net_amount + tax_amount`), so an issued invoice never changes when rules change.

## Migration guide

```bash
npm run db:up            # start PostgreSQL (Docker)
npm run db:migrate       # apply pending migrations
npm run db:info          # applied / pending
npm run db:validate      # checksums and naming
npm run db:test:prepare  # migrate the integration-test database (solo_test)
npm run db:reset         # LOCAL ONLY: wipe and re-migrate
```

Writing a migration:

1. Create `database/migrations/V<next>__<description>.sql`.
2. Follow the conventions above; add grants for `solo_app`.
3. `npm run db:migrate && npm run db:test:prepare`, then run `database/tests/schema_checks.sql`
   (`docker compose exec -T db psql -U solo_owner -d solo -f - < database/tests/schema_checks.sql`).
4. Add repository code and integration tests, including a cross-tenant test for new business data.

CI applies every migration to a fresh database, re-runs it (must be a no-op), validates it, and
upgrades a database from the previous version to the latest.
